# 01. 요구사항 정의

## 핵심 사용자 시나리오

---

### 시나리오 1 — 내국인 첫 예약

**페르소나**: 김민준 (25세, 대학생, 서울 → 부산 여행 계획)

```
1. 앱 실행 → 이메일로 회원가입
2. 홈 화면에서 출발지 "서울남부" 선택
3. 도착지 "부산종합" 선택
4. 날짜 선택 (내일)
5. 버스 목록에서 09:00 출발 조회
6. 원하는 좌석 선택 (창가 자리)
7. 결제 수단 선택 (일반카드) → 카드 정보 입력
8. 예약 확인 화면에서 최종 확인
9. 예매 내역에서 예약 확인
```

**핵심 니즈**: 빠른 좌석 확보, 직관적인 흐름

---

### 시나리오 2 — 외국인 관광객 예약

**페르소나**: Tanaka Yuki (28세, 일본인 관광객, 서울 → 경주 이동)

```
1. 앱 실행 → 언어 설정에서 "日本語" 선택
2. 카카오 계정으로 소셜 로그인
3. 터미널 검색창에 "Gyeongju" 입력
4. 검색 결과에서 "경주" 터미널 선택
5. 출발지 "서울고속버스터미널" 선택
6. 날짜/시간 선택 후 버스 목록 조회
7. 일본어로 표시된 좌석 안내 확인
8. 좌석 선택 → 결제 (카카오페이)
9. 예약 완료 화면을 캡처해 이동 수단으로 활용
```

**핵심 니즈**: 언어 장벽 없는 예약, 소셜 로그인으로 간편 가입

---

### 시나리오 3 — 재방문 사용자 빠른 예약

**페르소나**: 이수진 (32세, 직장인, 매월 고향 방문)

```
1. 앱 실행 → 자동 로그인
2. 즐겨찾기에서 "서울남부 → 전주" 바로 선택
3. 오늘 날짜 기준 버스 목록 자동 조회
4. 이전과 동일한 좌석 번호 선택
5. 자주 쓰는 카드로 결제 (저장된 카드 바로 선택)
6. 예약 완료
```

**핵심 니즈**: 반복 예약 최소 단계, 저장된 정보 재활용

## MoSCoW 기능 분류

### Must (반드시 있어야 함)

| 기능 | 설명 |
|---|---|
| 터미널 검색/선택 | 출발·도착지 검색, 지역별/인기순 목록 |
| 버스 목록 조회 | 날짜별 노선 및 잔여 좌석 수 표시 |
| 좌석 선택 | 좌석 배치도, 선택/불가 상태 표시 |
| 예약 확인 | 여행 정보, 탑승객 정보, 결제 금액 요약 |
| 다국어 지원 | 한/영/중/일 4개 언어 전환 |
| 공공 API 연동 | 실제 시외버스 노선 데이터 |
| 이메일 회원가입/로그인 | 자체 계정 인증 |
| 비회원 조회 | 로그인 없이 노선 검색 가능 |

---

### Should (있으면 좋음)

| 기능 | 설명 |
|---|---|
| 소셜 로그인 | 카카오 / 네이버 OAuth |
| 즐겨찾기 터미널 | 자주 쓰는 출발·도착지 저장 |
| 예매 내역 조회 | 과거/예정 예약 목록 |
| 결제 UI | 일반카드, 법인카드, 네이버/카카오페이 선택 화면 |
| 탑승인원 선택 | 일반/중고생/아동 인원별 요금 분리 |
| API fallback | 오류 시 로컬 샘플 데이터로 대체 |

---

### Could (여유 있으면 구현)

| 기능 | 설명 |
|---|---|
| 자주 쓰는 카드 등록 | 카드 정보 저장 및 빠른 선택 |
| 이벤트 / 쿠폰 | 할인 쿠폰 등록 및 적용 |
| 공지사항 | 앱 내 공지 목록 |
| 다크 모드 | 시스템 테마 연동 |
| 앱 튜토리얼 | 첫 실행 시 온보딩 화면 |

---

### Won't (이번 버전에서 제외)

| 기능 | 이유 |
|---|---|
| 실제 PG 결제 연동 | 졸업 작품 범위 초과, 사업자 등록 필요 |
| 실시간 버스 위치 추적 | API 미지원 |
| 채팅 고객센터 | 운영 인프라 필요 |
| 좌석 양도/취소 환불 | 실제 결제 미연동으로 의미 없음 |
| 푸시 알림 | FCM 서버 구성 필요 |

---

## 우선순위 로드맵

```
Phase 1 (Must)     → 핵심 예약 흐름 완성
Phase 2 (Should)   → 로그인·즐겨찾기·결제 UI
Phase 3 (Could)    → 부가 기능 (쿠폰, 공지 등)
```
