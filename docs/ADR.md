## ADR-001: 크로스플랫폼 프레임워크 — Flutter

| 항목 | 내용 |
|---|---|
| **상태** | Accepted |
| **날짜** | 2025-01 |

### 배경

Android·iOS 양 플랫폼을 단일 코드베이스로 개발해야 했다. 세 가지 선택지를 검토했다.

| 방식 | 특징 |
|---|---|
| **React Native** | 자바스크립트로 개발, 아이폰/안드로이드 네이티브 부품을 빌려 씀 → 플랫폼마다 UI가 조금씩 달라짐 |
| **Flutter** | Dart로 개발, 화면을 직접 그림 (네이티브 부품에 의존하지 않음) → 아이폰이든 안드로이드든 완전히 동일하게 보임 |
| **네이티브 분리 개발** | Swift(아이폰) + Kotlin(안드로이드) 따로 개발 → 코드를 두 번 짜야 하고 개발 인력도 두 배 필요 |

### 결정

**Flutter (Dart)** 를 채택한다.

- React Native는 네이티브 컴포넌트 의존도가 높아 플랫폼 간 미묘한 UI 차이가 발생함
- 네이티브 분리 개발은 코드를 두 번 짜야 해서 시간이 두 배로 걸림
- Flutter는 자체 렌더링 엔진(Skia/Impeller)으로 단일 코드베이스에서 완전히 동일한 UI 제공

### 결과

| 긍정 | 부정 |
|---|---|
| 단일 코드베이스로 Android·iOS 동시 지원 | Dart 언어 러닝커브 존재 |
| 플랫폼 간 완전히 동일한 UI | React Native 대비 커뮤니티 패키지 수 적음 |
| Hot reload로 빠른 UI 이터레이션 | 특정 네이티브 기능은 플러그인 의존 필요 |

## ADR-002: 버스 목록 정렬 기준 — 출발 시간순 고정

| 항목 | 내용 |
|---|---|
| **상태** | Accepted |
| **날짜** | 2025-02 |

### 배경

버스 목록을 사용자에게 보여줄 때 어떤 기준으로 정렬할지 결정이 필요했다. 후보: 출발 시간순, 가격순, 잔여 좌석순, 사용자 선택 정렬.

### 결정

**출발 시간 오름차순으로 고정** 한다.

- 사용자가 버스를 선택할 때 가장 먼저 확인하는 정보는 "몇 시에 출발하나"임
- 출발 시간순 정렬이 시각적으로 가장 직관적이고 예측 가능함
- 정렬 옵션 UI를 추가하면 화면이 복잡해지고 졸업 작품 범위를 초과함

### 결과

| 긍정 | 부정 |
|---|---|
| 사용자가 시간대별로 한눈에 파악 가능 | 가격순·잔여석순 정렬 불가 |
| 구현 단순 (추가 UI 불필요) | 사용자 정렬 선호도 반영 불가 |

## ADR-003: 실시간 좌석 조회 — 결정적 난수 시뮬레이션으로 대체

| 항목 | 내용 |
|---|---|
| **상태** | Accepted |
| **날짜** | 2026-05 |

### 배경

버스 예약 앱의 핵심 기능 중 하나는 실시간 좌석 현황 조회이다.
그러나 아래와 같은 이유로 실제 실시간 좌석 데이터를 가져오는 것이 불가능하다.

| 이유 | 설명 |
|---|---|
| **독점 유료 서비스** | 시외버스 실시간 좌석 API는 코버스(KOBUS)·금호고속 등 민간 업체가 독점 운영하며 외부에 비공개 |
| **공공 API 미지원** | 공공데이터포털 시외버스 API는 노선·시간표·요금만 제공, 실시간 잔여 좌석 미제공 |
| **B2B 계약 필요** | 실시간 좌석 연동은 터미널 사업자와 별도 계약 후 전용 키 발급 필요, 학생 프로젝트 접근 불가 |
| **비용 문제** | 민간 API 중개 서비스는 월 수십만 원 이상 유료 구독 모델 |

### 결정

**결정적 난수(Deterministic Random) 기반 좌석 시뮬레이션**을 사용한다.

- 버스 ID + 날짜를 seed로 `Random(seed)` 생성
- 동일한 버스·날짜는 항상 동일한 좌석 배치 반환 (재실행 후에도 일관성 유지)
- 탑승률 40% 기준으로 occupied / available 랜덤 배분

```dart
List<SeatStatus> generateSeats(String busId, String date) {
  final seed = int.parse(busId.replaceAll(RegExp(r'\D'), ''))
             + date.hashCode;
  final rng = Random(seed);
  return List.generate(28, (_) =>
    rng.nextDouble() < 0.4
      ? SeatStatus.occupied
      : SeatStatus.available);
}
```

### 결과

| 긍정 | 부정 |
|---|---|
| API 없이 현실적인 좌석 UI 시연 가능 | 실제 잔여 좌석과 다름 |
| 동일 버스·날짜는 항상 일관된 좌석 표시 | — |
| 구현 단순 (seed 기반 1개 함수) | — |

> 💡 **실 서비스 전환 시**: `generateSeats()` 함수를 실시간 API 호출로 교체하면 나머지 UI는 그대로 동작하는 구조로 설계됨.

## ADR-004: 에뮬레이터 GPS 한계 — 수동 위치 설정으로 대응

| 항목 | 내용 |
|---|---|
| **상태** | Accepted |
| **날짜** | 2026-06 |

### 배경

버스 앱의 지도 화면 현재 위치 표시 및 수면 모드의 목적지 도달 감지 기능은 GPS 위치 데이터에 의존한다.
개발·시연 환경이 Android 에뮬레이터이므로 아래와 같은 제약이 존재한다.

| 이유 | 설명 |
|---|---|
| **GPS 칩 부재** | 에뮬레이터는 가상 머신이므로 실제 GPS 수신 칩이 없음 |
| **위성 신호 없음** | 물리적 위성 신호 수신 하드웨어가 없어 실시간 위치 변화 추적 불가 |
| **위치 초기화** | 재시작 시 위치가 기본값(미국 마운틴뷰 등)으로 리셋됨 |

### 결정

**Android Studio Extended Controls의 Location 탭으로 수동 위치 설정**한다.

```
에뮬레이터 우측 ⋮ 버튼 → Location 탭
→ Latitude / Longitude 입력 → Send 버튼
```

| 항목 | 값 (서울 기준) |
|---|---|
| Latitude | 37.5665 |
| Longitude | 126.9780 |

### 결과

| 긍정 | 부정 |
|---|---|
| 추가 도구 없이 에뮬레이터만으로 GPS 기능 시연 가능 | 이동 시뮬레이션(경로 추적) 불가 |
| 수면 모드 알림 테스트를 원하는 좌표로 자유롭게 수행 가능 | 매 세션마다 좌표를 수동으로 입력해야 함 |
| 실기기 없이 위치 관련 UI 전체 검증 가능 | 실시간 위치 추적은 실기기에서만 최종 검증 가능 |
